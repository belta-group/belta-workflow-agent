# 部署別ロールブック（roles.md）

部署ごとの役割・典型業務・ツール利用傾向・成果物の型を定義するカタログ。エージェントを利用者の**部署の業務に合わせてパーソナライズする**ための知識源（cc-company `departments.md` の BELTA 向け移植）。

## 使われ方

1. オンボーディングで部署を収集（→ `profile.md` の `department`）。
2. その部署に一致するセクションを本ファイルから引き当て、**プライマリロール** `~/.belta/roles/<slug>.md` として展開し、索引 `~/.belta/roles/ROLES.md` に `primary` として記録する。
3. 運営モードで毎セッション `profile.md` + `ROLES.md`（索引） + プライマリロールを文脈に入れる。話題が他のロールの領域に触れたら、そのロールファイルもその場で読み込む（段階的開示）。

> **プライマリは 1 つ、ロールは複数育つ**。オンボーディング時点では所属部署のロールだけを作り、その後の利用状況から必要な部署ロール（マーケティング・デザイン・開発など）を**エージェント側から提案して増やしていく**（cc-company の「社内に部署が揃っていく」モデル）。該当部署が未詳細なら下の「汎用ロール雛形」を使う。

## ロールの提案と成長（エージェント主導）

ロールは「利用者が書く設定ファイル」ではなく、**エージェントが観察し、提案し、承認を得て育てるもの**。利用者の直接編集も歓迎するが、基本サイクルは **観察 → 提案（`AskUserQuestion`） → 承認 → 反映** をエージェント側が回す。

### 新しい部署ロールの提案（新設）

利用者の依頼が既存ロールのどれにもカバーされない部署領域（例: マーケティング、デザイン、開発、経理）に **別々の機会で 2 回以上** 及んだら、その部署ロールの新設を `AskUserQuestion` で提案する：

> 「最近◯◯系のご依頼が続いています。**マーケティング部署のロール**を秘書に追加しますか？ 追加すると、この領域の依頼で典型業務・成果物の型・主担当ツールの既定が効くようになります」

承認されたら、本ファイルに詳細セクションがあればそれを、無ければ「汎用ロール雛形」に観察した典型業務を流し込んで `~/.belta/roles/<slug>.md` を生成し、`ROLES.md` に記録する。反復検知フック（`repeat-detect.js` / `session-start.js`）がパーソナライズ提案を促したときも、ルール化・エージェント化と並んでロール新設を検討する。

### 既存ロールのブラッシュアップ（成長）

既存ロールの領域で次が観察されたら、該当 `roles/<slug>.md` への追記・修正を `AskUserQuestion` で提案し、承認後に Edit で反映して `ROLES.md` の `updated` を更新する：

- 新しい典型業務・成果物の型・段取り・用語が繰り返し現れた（ロールにまだ書かれていない）
- 利用者がロールの既定と**違うやり方を 2 回以上**選んだ（既定が実態とズレている）
- 完了した仕事から「次も使える型」が抽出できた（フォーマット・チェックリスト・定番の宛先）

> ブラッシュアップは**差分を見せて承認を得てから**反映する（勝手に書き換えない）。利用者が自分で編集した行は尊重し、上書き提案するときはその旨を明示する。

### 却下の扱い

同一の提案（新設・ブラッシュアップとも）を **3 回連続で却下されたら 14 営業日の冷却**（提案停止）。`ROLES.md` の管理コメントに rejected を記録する（他の提案系スキルと統一）。

### 住み分けと優先順位

- **ロール（roles/）** ＝ 部署の文脈・既定（常時または話題時に読む**知識**）。**agent-learning の subagent** ＝ 隔離実行する**担当者**。同じ領域で両方が育ってよい（例: マーケのロールが文脈を与え、マーケ分析 subagent が実行する）。振る舞いの恒久ルールは rule-learning へ橋渡しする。
- 優先順位は **`profile.md`（明示プロフィール） > `RULES.md`（明示ルール = rule-learning） > ロール（`roles/`、部署の既定） > `user-model.md`（観察ベースの暗黙傾向）**。ロールは「部署の既定」であって、利用者個別の明示指示を上書きしない。

### ROLES.md（索引）形式

```markdown
# ロール索引（このファイルは毎セッション読み込まれる）
- [info-system](info-system.md) — 情報システム部 | primary | created:2026-06-12 / updated:2026-06-12
- [marketing](marketing.md) — マーケティング | adopted:2026-06-15 / updated:2026-06-20
<!-- rejected: <slug> | <部署> | rejected (n) | last:YYYY-MM-DD -->
```

## Phase -1 の範囲

- **情報システム部のみ詳細記述**（Phase -1 の社内試用検証者＝内田氏の所属部署）。
- 他部署は「汎用ロール雛形」で代替し、実利用者が出た部署から順に詳細化する。
- 残部署の詳細化は Phase 1 期間内（〜2026-06-30）に拡充予定（`docs/tasks.md` Phase 1 配布後タスク）。

## 情報システム部（詳細）

### ミッション

社内の情報基盤・業務ツール（Notion / Slack / Google Workspace / GitHub 等）を整備・運用し、各部署の業務効率化を技術面から支える。自部署では「仕組みで解く」ことを志向し、属人化を避ける。

### 既定の機密度

**社外秘** を基準とする（社内システム構成・アカウント情報・問い合わせ内容を扱うため）。人事・経営に関わる問い合わせ対応時は **極秘** に引き上げる。

### 主要業務

#### 1. Notion スキーマ設計

- **典型タスク**: 各部署の業務に合わせた Notion DB（タスク / 議事録 / ナレッジ / 案件台帳など）の設計・構築・改善。
- **使うツール**: Notion（claude.ai Connector）。DB 設計は `notion-schema` サブスキルに委譲する。
- **成果物の型**: 正規化された DB（`STATUS`/`SELECT` 中心、relation 最小限、View 3 セット）。設計時は[ベストプラクティス](../../notion-schema/references/best-practices.md)とアンチパターンを必ず適用。
- **ポイント**: 「全部 1 DB に詰める」「Status をテキストにする」等のアンチパターンを各部署に作らせない。設計意図を相手部署が保守できる粒度で残す。

#### 2. 週次ワークフロー改善

- **典型タスク**: 自部署・他部署の定例業務の棚卸し、ボトルネック特定、手作業の自動化提案。
- **使うツール**: Notion（タスク/ナレッジ）+ Slack（連絡・周知）+ GitHub（スクリプト・設定管理）。横断依頼は順序立てて 1 つずつ実行。
- **成果物の型**: 改善前後の手順比較、削減時間の見積り、Notion 上の改善ログ。
- **ポイント**: 繰り返し手作業を検知したら rule-learning / skill-suggestion の自動提案につなげる。

#### 3. 社内問い合わせ対応

- **典型タスク**: アカウント・権限・ツール操作・トラブルの問い合わせ受付と回答、FAQ 化。
- **使うツール**: Slack（受付・回答）+ Notion（ナレッジ/FAQ 蓄積）+ Google Drive（手順書・資料）。
- **成果物の型**: 回答 + 再利用可能な FAQ/手順書（Knowledge パターン、`機密度`・`最終レビュー` プロパティ必須）。
- **ポイント**: 同じ問い合わせが繰り返されたらナレッジ化し、次回は参照で即答できるようにする。個人情報を含む問い合わせは外部送信前に確認（PII フックが二重で守る）。

### 用語・対象システム

- 対象システム: Notion / Slack / Google Workspace（Drive・カレンダー・Gmail）/ GitHub / 各種 SaaS。
- よく出る語: 「スキーマ」「DB（データベース）」「relation」「rollup」「権限（permission）」「棚卸し」「FAQ 化」「自動化」。

### ツール利用の傾向

| 場面 | 主担当ツール |
| --- | --- |
| 設計・蓄積（DB・ナレッジ・FAQ・タスク） | Notion |
| 連絡・周知・問い合わせ受付 | Slack |
| 資料・手順書・スプレッドシート | Google Drive |
| スクリプト・設定・IaC・PR レビュー | GitHub（`gh` CLI） |

## 汎用ロール雛形（未詳細部署用）

該当部署のセクションが無い場合に使うテンプレート。ロール（`roles/<slug>.md`）生成時にこの枠へ、プライマリなら profile.md の主要業務を、提案による新設なら観察した典型業務を流し込む。

```markdown
# ロール: <部署名>

## 既定の機密度
<公開 | 社外秘 | 極秘>（profile.md に従う）

## 主要業務
- <業務1>: 典型タスク / 使うツール / 成果物の型
- <業務2>: 〃
- <業務3>: 〃

## ツール利用の傾向
- 設計・蓄積 → Notion
- 連絡・周知 → Slack
- 資料・ファイル → Google Drive
- コード・PR → GitHub（gh CLI）

## メモ
- この部署はまだ詳細化されていない（汎用雛形で運用中）。
- 運用で得た典型業務・用語・成果物の型を蓄積し、Phase 1 で本ファイルに詳細セクションを追加する。
```
