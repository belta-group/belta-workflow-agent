# 自動ルール化（rule-learning）

要件 5「個々人にパーソナル化される仕組み」の核心。利用者の好み・ミスの傾向・繰り返し指示を **テキストのルール** として `~/.belta/rules/` に蓄積する。蓄積したルールはインデックス `RULES.md` を通じて以降のセッションの文脈に載り、エージェントが同じ訂正を繰り返させない。

ルールに収まらない「業務領域そのもの」の繰り返しは [agent-learning](../agent-learning/SKILL.md) が、既存スキルで賄えない非効率作業は [skill-suggestion](../skill-suggestion/SKILL.md) が担当する。本スキルは **テキスト指示として一般化できる粒度** を扱う。

## いつ使うか（検知トリガ）

`workflow` 運営モードの会話中、次のいずれかを検知したら本スキルを起動する。**1 つでも当てはまれば候補化**してよい。

### トリガ A: 発話フレーズ検出

利用者の発話に、恒常的な指示を示すフレーズが含まれる：

- 「次回からは」「今後は」「これからは」「毎回」「いつも」「常に」
- 「前にも言ったけど」「さっきも言ったが」「何度も言うけど」
- 「〜しないで」「〜は避けて」を恒常条件として述べたもの

> 一度きりの依頼（「今回はこうして」）はルール化しない。**恒常性**を示す語が鍵。

### トリガ B: 同じ訂正パターンの 2 回以上検出

**同一セッション内**、または `~/.belta/notes/` の直近記録を参照し、**利用者が同種の訂正を 2 回以上**（同じ会話の中での繰り返しでも、別々の機会での繰り返しでも）行った場合：

- 例: 2 回続けて「日付は YYYY-MM-DD で」と直された
- 例: Slack 共有のたびに「冒頭に要約を付けて」と直された

判定は完全一致でなく **訂正の意図が同じか**（LLM 判定）で行う。2 回目を検知した時点で候補化する。

### トリガ C: 非自明な選択を採用した直後の肯定

エージェントが複数の選択肢から **非自明な判断** を提示し、利用者が「それで正解」「完璧」「まさにそれ」等で強く肯定した場合、その判断基準をルール化候補にする。

## 自動化フロー

### Step 1: 候補を 1 つに絞って提示

検知したら、ルール本文の要点を **1〜2 文** に要約し、利用者に確認する：

> 「○○というルールとして `~/.belta/rules/` に保存しておきますか？（次回以降このセッションをまたいで反映されます）」

- 提案は **AskUserQuestion**（保存する / 今回は不要、の 2 択 + 自由記述）で出すと迷いがない。
- 一度に複数のルールを提案しない。最も確度の高い 1 件に絞る。

### Step 2-a: 承認 → 保存

1. `slug` を kebab-case で決める（例: `date-format-iso`, `slack-summary-first`）。既存ファイルと衝突しないこと。
2. [references/rule-template.md](references/rule-template.md) の frontmatter 雛形に沿って `~/.belta/rules/<slug>.md` を **Write ツールで作成**する。`type` は preference / mistake-fix / workflow / domain-knowledge から選ぶ。`source` には検知トリガ（発話または操作）を簡潔に残す。
3. インデックス `~/.belta/rules/RULES.md` に 1 行追記する（後述「RULES.md の管理」）。
4. 「保存しました。次回からこのルールを尊重します」と一言返す。

### Step 2-b: 拒否 → rejected 記録

利用者が「不要」とした場合、`~/.belta/rules/.rejected.md`（無ければ作成）に 1 行追記する：

```
- <YYYY-MM-DD> | <候補slug> | <要約> | rejected (1)
```

- **同じ候補は 3 回目までは再提案しない**。`.rejected.md` の同一候補の回数を数え、`(1)`〜`(2)` の間は沈黙する。`(3)` 到達後は提案を完全停止する。
- 回数は「意図が同じ候補」でまとめる（slug 完全一致でなく LLM 判定）。

## RULES.md の管理（常に LLM 文脈に読込）

`~/.belta/rules/RULES.md` は運営モードの起動時に毎回 Read される **インデックス**。個別ルールの全文ではなく 1 行サマリだけを持つ（省トークン）。

### 初期化（無ければ作成）

`RULES.md` が存在しない状態で初めてルールを保存するときは、まず次の内容で新規作成してから 1 行追記する：

```markdown
# RULES — 学習済みルール索引

このファイルは `rule-learning` が自動生成・追記する。運営モード起動時に毎回読み込まれ、
各ルールの本文（`<slug>.md`）は必要時のみ Read する。1 ルール 1 行・上限 200 行。

<!-- 追記形式: - [<slug>](<slug>.md) — <description> -->
```

### 追記形式

```
- [date-format-iso](date-format-iso.md) — 日付は常に YYYY-MM-DD 形式で出力する
```

### 上限と統廃合

- **上限 200 行**。超えそうになったら、重複・陳腐化したルールの統合を利用者に提案する（自動削除はしない）。
- ルールが矛盾した場合は新しいものを優先しつつ、古い方の扱い（更新 / 削除）を確認する。

## 運用上の原則

- **必ず利用者承認を挟む。** 検知しても無断で保存しない。
- 機密値（パスワード・トークン・個人情報）はルール本文に書かない。「○○の認証情報を使う」等の **参照のみ** に留める（[security-policies.md](../workflow/references/security-policies.md) §5）。
- パスはホームディレクトリ環境変数（POSIX: `$HOME` / Windows: `%USERPROFILE%`）から解決し、区切り文字を直書きしない。ファイル作成は Write ツールを使い、`mkdir` / `touch` 等の POSIX コマンドを必須経路に置かない（Mac / Windows 両対応）。
- `~/.belta/` 配下はすべて `.gitignore` 対象。リポジトリにコミットしない。
