# 利用者向けドキュメント執筆規約（非エンジニアにも伝わる文章）

`docs/` 配下の **利用者向けドキュメント**（VitePress サイト）を新規作成・改訂するときの必須規約。読者は「Claude Code を業務で使うが、エンジニアではない社員」。エンジニア前提の書き方（背景から長々と説明する／横文字を訳さない／一度に詰め込む）は、この読者の前で黙って伝わらなくなる。**一読で伝わること**を必須要件とする。

> 適用範囲: `docs/` の利用者向けページ（`index.md` / `guide/*.md`）。担当者向けの内部資料（`docs/background.md` / `docs/tasks.md`）やプラグイン内部の技術リファレンス（`plugins/**`）には強制しないが、精神は流用してよい。

## 1. 5 原則（すべてのページに適用）

1. **結論（ゴール）を先に出す** — 各ページ・各セクションの冒頭で「これは何の話で、読むと何ができるか」を 1〜2 文で宣言する。背景・経緯から始めない。「**結論から言うと** —」で始める文を置くと外しにくい。
2. **認知負荷を最小化する（引き算）** — 1 セクション 1 メッセージ。情報を削り、段階を分ける。長い表は、要点を文章で先に述べてから補助的に置く。
3. **メタファーで「絵」にする** — 抽象概念は身近な例えに変換する。下記 §3 の統一メタファーを使い、ページ間でブレさせない。
4. **専門用語を翻訳する** — 横文字・専門用語は「**日常語（専門用語）**」の形で必ず言い換える。下記 §4 のグロッサリーで表記を統一する。
5. **ピラミッド構造で並べる** — 結論 → 理由 → 具体例 の順。思いついた順に書かない。

## 2. 認知状態への配慮（話し方の原則）

- 説明を始める前に「これは何の話か」を一言で渡し、読者の頭に**地図**を先に置く。
- 短く書くことは、読者の時間と集中力を尊重する礼儀である。冗長な前置き・重複を削る。
- 自分の「当たり前」を捨て、相手が分からない前提で言葉を選ぶ（知識の呪いの打破）。

## 3. 統一メタファー（この言い回しで固定）

| 対象 | 言い回し |
| --- | --- |
| 本エージェント全体 | 「4 つのアプリ（Notion・Slack・GitHub・Google Drive）を使い分ける、あなた専用の秘書」 |
| OAuth 接続 | 「合鍵を渡さず、訪問のたびにインターホンで『どうぞ』と許可するイメージ。アプリの『許可』ボタンを押すだけ」 |
| 3 層セキュリティ（L1/L2/L3） | 「空港の保安検査のように、何重ものゲートで機密の持ち出しを止める。1 つ抜けても次が止める」 |
| パーソナライズ | 「使うほど手に馴染む道具／あなたの口ぐせや段取りを覚えてくれる秘書」 |
| 自動エージェント化 | 「同じ種類の仕事が増えたら、その仕事専門の担当者を新しく雇うイメージ」 |

新しいメタファーを足すときは、既存と矛盾しないこと。原則 1 ページ 1〜2 個に留め、例えの過剰投入で逆に重くしない。

## 4. 用語グロッサリー（「日常語（専門用語）」で統一）

| 専門用語 | 言い換え |
| --- | --- |
| エージェント | アシスタント（秘書） |
| OAuth | 「許可」ボタンで安全につなぐ方式（OAuth） |
| Connector / コネクター | claude.ai の接続設定（Connectors） |
| MCP / MCP ツール | アプリ連携機能（MCP） |
| PAT / API キー | 長いパスワードのような接続キー（API キー） |
| permission / allowlist | 操作ルール（やってよい allow／確認する ask／禁止 deny） |
| hook / フック | 自動で働く見張り役（フック） |
| PII | 個人情報（マイナンバーやカード番号など） |
| 専用エージェント / subagent | その仕事専門のアシスタント |
| gitleaks | 機密の混入を見つける検査 |
| gh / gh CLI | GitHub 用の小さな道具（gh） |
| device flow | 画面のコードを入力して許可する方式 |
| symlink | ショートカット（分身） |
| keychain / 資格情報マネージャー | OS が暗号化して鍵を保管する金庫（OS 標準資格情報ストア） |
| セッション | Claude Code を開いている 1 回の会話 |

このリストにない用語が出たら、同じ「日常語（専門用語）」形式で訳し、必要なら本リストに追記する。

## 5. 体裁（VitePress）

- **結論・注意・補足は VitePress コールアウトで視覚分離する**：`::: tip`（要点・コツ）／`::: info`（補足）／`::: warning`（注意）／`::: danger`（事故時の手順など強い警告）。
- `~/.belta/...` などのパスを出すときは「あなたのパソコン内の個人フォルダ（`~/.belta/`）」のように一言補足する。ホーム表記はシェルの `~` に依存させず「POSIX: `$HOME` / Windows: `%USERPROFILE%`」を併記する（`cross-platform.md §2` と整合）。

## 6. 厳守する制約（壊さないもの）

- **frontmatter（`---` で囲う部分）を壊さない。**
- **既存の `##` / `###` 見出しの文言を安易に変更しない。** 他ページがその見出しにアンカーリンク（`#l1-pii-検知フック` 等）しているため、文言を変えるとリンクが切れる。見出しは据え置き、その下に結論文・例え・言い換えを足すのが基本。どうしても変える場合は、参照側のアンカーも全て追従修正する。
- **内部リンク（`/guide/...`）とアンカーを壊さない。**
- **技術的正確さを落とさない。** 担当者向けの精密情報（検知ロジック・保管先・権限境界など）は残す。ただし「日常語の説明を前、精密表を後」の順にする。
- コードブロック内の実コマンド（`/workflow`・`gh auth login --web`・`node ".../*.js"` 等）は勝手に書き換えない。

## 7. 検証

- 改訂後は必ず VitePress をビルドして dead-link / アンカー切れが無いことを確認する：`cd docs && npm run docs:build`（`ignoreDeadLinks` は localhost のみ許容のため、内部リンク切れはビルドで落ちる）。
- アンカー対象の見出しを変更していないか grep で確認する。
- 「結論が冒頭にあるか」「横文字が訳されているか」「1 セクション 1 メッセージか」を、各ページでセルフレビューする。
