# スキル作成規約（効果的な SKILL.md の作り方）

このプラグインが **スキルを新規作成・改訂する**ときの必須規約。対象は本リポジトリ同梱スキル（`plugins/workflow/skills/*/SKILL.md`）と、`skill-authoring` が利用者環境に自作するスキル（`<agent_home>/.claude/skills/<name>/`）の両方。

> **大原則**: スキルは「ただの指示書（Markdown 1 枚）」ではなく、**指示・スクリプト・参照知識・アセットを内包した「AI 専用の道具箱（フォルダ）」** として設計する。Claude Code が必要なときに必要なファイルだけを自律的に発見・読込・実行できる構造そのものが価値になる。出典: [Lessons from building Claude Code: How we use skills](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills)。

## 1. 1 スキル 1 役割（カテゴリーを 1 つに絞る）

役割を詰め込むと AI が混乱し、誤発火・精度低下を招く。新規スキルは次の 9 カテゴリーの **いずれか 1 つ**に明確に合致させる。複数にまたがるなら分割する。

| # | カテゴリー | 概要 |
| --- | --- | --- |
| ① | ライブラリ・API リファレンス | 社内ライブラリ / CLI / SDK の正しい使い方と「罠（Gotchas）」の集約 |
| ② | プロダクトの検証（テスト） | Playwright 等と組み合わせた動作確認。**最も品質向上に効くカテゴリ** |
| ③ | データ取得と分析 | モニタリング（Grafana / Datadog）・データ基盤への接続と定番クエリ |
| ④ | 業務プロセス・チーム自動化 | チケット作成・Slack 報告・週次まとめ等の反復ワークフロー |
| ⑤ | コード生成・テンプレート | 雛形生成（自然言語での細かな要件定義が要る場合に有効） |
| ⑥ | コード品質とレビュー | 静的解析の実行、別人格（subagent）による厳しい批評 |
| ⑦ | CI/CD とデプロイ | 壊れた CI の再試行・コンフリクト解消・カナリア監視 |
| ⑧ | ランブック（障害対応手順書） | アラート検知時に複数ツールを横断調査し構造化レポートを生成 |
| ⑨ | インフラ運用 | 不要リソースのクリーンアップ・依存管理・コスト急増調査 |

## 2. 当たり前を書かない（AI が苦手な領域に絞る）

Claude は既に高度なコーディング知識を持つ。「普通のコードの書き方」を重複指示しても無駄にトークンを食うだけ。**AI が標準では苦手とする領域**（独自の UI 制約、社内固有の作法、外部からは推測できない手順）だけを書く。

## 3. 「罠（Gotchas）」セクションを最重要視する

**過去に AI が実際に失敗した具体パターン**の蓄積が、スキルの効果を最も押し上げる。汎論ではなく再現可能な落とし穴を箇条書きで残す。

> 例: 「このテーブルは追記型（Append-only）。最新行は `created_at` の最大ではなく `version` が最大の行を取ること」

このプラグインでは、`hallucination-memory`（事実訂正）や `rule-learning`（振る舞い訂正）で検知した再発誤りを、関連スキルの Gotchas に逆流させると効果が高い。

## 4. ファイルシステムと「段階的開示（Progressive Disclosure）」

すべてを 1 ファイルに詰めない。`SKILL.md`（メイン）を入口に、詳細は小分けする。フォルダ構造そのものがコンテキスト整理（Context Engineering）になり、AI は必要時に必要なファイルだけを読む。

- `SKILL.md` — 入口。発火条件・全体像・どの補助ファイルをいつ読むかの誘導。
- `references/*.md` — 参照知識（API 詳細・テンプレート・ドメイン知識）。
- `scripts/*.js` — 補助スクリプト（**Node.js 単一実装**。`cross-platform.md` 準拠。後述 §8）。
- `assets/*` — 雛形・テンプレート等の静的アセット。

## 5. description は「人間」ではなく「AI」に向けて書く

Claude Code がセッション開始時にまず読むのは各スキルの `description`。ここが発火マッチングの精度を決める。

- AI が「このタスクにはこのスキルが使える」と判断できる**キーワード・目的・業務ドメイン語**を明記する。
- **狭く具体的に**。広すぎる description は無関係な場面で誤発火し、毎回トークンを浪費する。発火条件（トリガー語・適用場面）と、必要なら非適用条件（SKIP 条件）も書く。

## 6. AI を縛りすぎない（柔軟性を残す）

手順をガチガチに固定（レールロード）すると、状況に応じた臨機応変さが失われる。**ゴールと制約・罠**を伝え、達成手段は AI の判断に委ねる。固定すべきは「守らないと壊れる箇所」だけにする。

## 7. 初期設定（セットアップ）を設計に織り込む

Slack のチャンネル ID 等、利用者ごとに変わる設定値は SKILL.md 本文に直書きせず、スキル内の設定ファイル（`config.json` 等）に分離する。**設定が無い場合は、AI が `AskUserQuestion` で利用者に自発的に質問して埋める**よう SKILL.md に指示する。機密値（トークン・パスワード・個人情報）は本文に直書きせず「○○の認証情報を使う」等の参照に留める。

## 8. このプラグイン固有の制約（必ず重ねて守る）

スキル作成は上記の一般原則に加え、本リポジトリの既存規約に従う。

- **クロスプラットフォーム**: 同梱スクリプトは Node.js 単一実装。`mkdir -p` / `cp` / `ln -s` / `cat` 等の OS 依存コマンドを必須経路に置かない（`cross-platform.md`）。パスは `os.homedir()` / `path.join()` で解決。
- **権限境界を広げない**: 生成スキルは新たな権限を獲得しない。利用ツールは親 `.claude/settings.json` の `permissions`（allow / ask / deny）に従い、PII 検知フック（`hooks/pre-tool-use.js`）がそのまま発火する前提で設計する。
- **配置と索引**: 自作スキルの実体は専用フォルダ `<agent_home>/.claude/skills/<name>/` に Write で直接置く（symlink/コピーはしない）。発火・採用追跡の索引は `~/.belta/skills/AUTHORED.md`。詳細は [skill-authoring](../../plugins/workflow/skills/skill-authoring/SKILL.md)。
- **自作の発火ゲート**: 利用者環境への新規スキル自作は最も侵襲的なため、`skill-authoring` の消去法ゲート（rule / agent / 既存スキル導入で賄えず、専門業務が 3 回以上反復）を満たすときのみ。

## 9. 検証

- スクリプトを同梱したら `node --check <path>` で構文チェック（OS 依存処理を書いたら必須）。
- `description` のセルフレビュー: 「対象タスクで確実に発火するか」「無関係な場面で誤発火しないか」を発火トリガー語の観点で確認する。
- 段階的開示のセルフレビュー: 「`SKILL.md` だけで全体像と誘導が完結するか」「詳細が `references/` に適切に外出しされているか」。
