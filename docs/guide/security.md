# セキュリティと権限

**ひとことで言うと**：このページの仕組みは、あなたが Notion / Slack / Google Drive / GitHub に何かを送ったり保存したりするとき、**マイナンバーやカード番号などの機密が、うっかり外に出ないように見張る安全装置**です。普段の操作は妨げません。機密が混じったときだけ止まります。

::: tip まず結論：普段は止まりません
読むだけ・調べるだけ・機密を含まない書き込みは、これまで通りスムーズに進みます。**個人情報（マイナンバーやカード番号など）や「社外秘」ラベルが混じったまま外に出そうとしたときだけ**、自動で止まります。難しい設定を覚える必要はありません。
:::

この仕組みは、**空港の保安検査のように、何重ものゲートで機密の持ち出しを止めます。1 つ抜けても次が止める**――という考え方でできています。ゲートはそれぞれ独立して働きます。

- **L1：送信ボタンの直前に立つ最後の検査官**（自動で働く見張り役＝フック）。マイナンバーやカード番号が混じっていたら止める。**鍵やパスワードが入ったファイル（`.env` や SSH 鍵）を開こうとしたときも止める**。
- **L1.5：入館証のチェック**（スキルの許可リスト）。導入した覚えのない道具（スキル）が動こうとしたら、一声確認する。
- **L2：操作ごとの通行許可証**（操作ルール＝permission）。見るだけは自由、送る・作るは一声確認、危険な操作は通行禁止。
- **L2.5：仮想の個室で作業する**（サンドボックス）。読み書きできる場所と連絡先をあらかじめ決めておき、うっかりした事故が部屋の外へ広がらないようにする。
- **L2.6：出入りを許した業者だけ通す**（つなげるアプリの許可リスト）。Notion・Slack・Google Drive など、許可したアプリ連携以外は使えない。
- **L3：保存（コミット）するときに荷物の中身をスキャンする検査ゲート**（機密の混入を見つける検査＝gitleaks）。

これらの手前には、**L0：エージェント運用ルール**（送る前に内容を確認し、機密度を尊重する習慣）も働いています。

下の表は上の説明をまとめたものです。詳細は各セクションで説明します。

| 層 | 役割（たとえ） | 実装 | 守る境界 | タイミング |
| --- | --- | --- | --- | --- |
| **L1: PII 検知フック** | 送信直前の最後の検査官 | `hooks/pre-tool-use.js` | 外部送信・書き込みツールの呼び出し／鍵ファイルの読み取り | 実行**直前**にブロック |
| **L1.5: スキル許可リスト** | 入館証のチェック | `hooks/skill-gate.js` | 導入記録のないスキルの起動 | 起動**直前**に確認 |
| **L2: permission allowlist** | 操作ごとの通行許可証 | `.claude/settings.json`（allow / ask / deny） | ツール実行可否そのもの | 呼び出し判定時 |
| **L2.5: サンドボックス** | 仮想の個室 | `.claude/settings.json` の `sandbox` | コマンドが触れるファイルと通信先 | 実行**中ずっと**（OS が強制） |
| **L2.6: MCP 許可リスト** | 出入りを許した業者だけ通す | `.claude/settings.json` の `allowedMcpServers` | 使えるアプリ連携そのもの | 接続時 |
| **L3: Git 漏洩防止** | 保存時の荷物スキャン | `.gitleaks.toml` + GitHub Actions | リポジトリへの commit / push | コミット・CI 時 |

::: info なぜこれだけ層が必要なのか
L1・L2 は「秘書が使おうとした道具」を見て判断します。ただし、その道具の中で動くプログラムが自分でファイルを開くところまでは追えません。L2.5（仮想の個室）は**パソコンの OS 自身が境界を守る**ので、秘書が何をしようとしたかに関係なく効きます。逆に個室はコマンド実行にだけ効き、ファイルの読み書きやアプリ連携には及びません。**得意分野が違うので、両方が必要**です。
:::

## 機密度 3 段階

**結論**：最初のオンボーディングで選んだ「この情報はどれくらい秘密か」の設定が、すべての検査の厳しさを決めます。秘密度が高いほど、検査官は慎重になります。

設定は `~/.belta/profile.md`（POSIX: `$HOME` / Windows: `%USERPROFILE%` から解決）の `confidentiality` に記録されます。3 段階の意味は次のとおりです。

| 機密度 | 意味 | 外部送信前の扱い |
| --- | --- | --- |
| **公開** | 社外に見せてよい情報が中心 | 通常の確認 |
| **社外秘** | 社内限定。社外への流出は禁止 | 送る前に内容を要約して確認 |
| **極秘** | 個人情報や経営情報など最高機密 | 外部送信は原則避ける。必要なときは厳しく確認し、個人情報の検知も強めに解釈 |

## L1: PII 検知フック

**結論**：これは「**送信ボタンの直前に立つ最後の検査官**」です。あなたが何かを送る・保存するその瞬間、中身に個人情報（マイナンバーやカード番号など。専門用語で PII）が混じっていないかを自動で見張る役（フック）です。見つけたら操作を止め、その箇所を消す・隠す、あるいは外に出さない方法に切り替えるよう促します。

なぜ「直前」かというと、許可を出した後でも、文章の中に機密がまぎれ込むことがあるからです。最後の関所で実物をもう一度確かめる、という役割です。

### 検知対象

検査官が「これは個人情報かも」と見分ける主な手がかりは次のとおりです。むやみに止めすぎないよう、誤検知を抑える工夫も入っています（たとえばカード番号は、桁の並びが数式的に正しいものだけを対象にします）。

| 種別 | 見分け方（検知ロジック） | 止めすぎない工夫（誤検知抑制） |
| --- | --- | --- |
| クレジットカード番号 | 16 桁（4 桁 ×4、区切りは任意） | カード番号の正しさを数式でざっと確かめる手法（**Luhn 検証**）に通った候補のみ |
| マイナンバー | 12 桁（4-4-4） | 続く 16 桁（カード番号）は境界で区別して除外 |
| メールアドレスの一括掲載 | `@` を含むアドレス | **異なるアドレスが 5 件以上**で発火（1 件だけなら通す） |
| 機密ラベル | `マル秘` / `㊙` / `社外秘` / `Confidential`（大文字小文字は無視） | — |
| パスワードの直書き | `password` の直後に `:` または `=` | — |

### 対象となるツール

**結論**：検査官が立つのは「送る・作る・書き込む」操作の前だけです。読むだけ（検索・閲覧・一覧）はそのまま通します。荷物を持ち出すゲートにだけ検査官がいる、というイメージです。

対象になる主な操作は次のとおりです。

- **Slack**: `slack_send_message` / `slack_send_message_draft` / `slack_create_canvas` / `slack_schedule_message` / `slack_update_canvas`
- **Notion**: `notion-create-*` / `notion-update-*` / `notion-create-comment` / `notion-duplicate-page` / `notion-move-pages`
- **Google Drive**: `create_file` / `copy_file`
- **GitHub（Bash）**: `gh issue/pr create|comment|edit` / `gh release|gist create` / `gh api --method POST|PATCH|PUT`
- **HTTP クライアント（Bash）**: `curl` / `wget` / `http`

::: tip 利用者から見た挙動
普段の読み取りや、機密を含まない書き込みは妨げられません。**マイナンバーやカード番号、「社外秘」ラベルなどを含んだまま外部送信しようとしたときだけ**ブロックされます。その場合は、該当箇所を除いて送り直してください。
:::

### 鍵やパスワードが入ったファイルの読み取りをブロック

**結論**：`.env`（アプリの接続キーを書くファイル）や SSH 鍵といった、**鍵やパスワードが入っているファイルを開こうとする操作は止まります**。中身を見なくても仕事ができるはずの場面で、うっかり鍵を画面や送信先に持ち出すのを防ぐためです。

止まる対象は次のとおりです。

| 種別 | 例 |
| --- | --- |
| 接続キーのファイル | `.env` / `.env.local` / `secrets.env` |
| サーバーにつなぐ鍵 | `~/.ssh/` の中身 / `id_rsa` |
| 証明書・秘密鍵 | `*.pem` / `*.key` |
| クラウドの認証情報 | `~/.aws/` / `~/.config/gh/` |

::: tip 止まりすぎないようにしてあります
- **サンプルファイルは通ります**：`.env.example` / `.env.sample` / `.env.template` / `.env.dist` は、鍵ではなく「書き方の見本」なのでそのまま読めます。
- **文字列として探すだけなら通ります**：「`.env` という言葉がどのドキュメントに出てくるか探す」といった検索は止まりません。
- どうしても正当なファイルが止まってしまう場合は、例外を 1 つ追加できます（`environment.env` のような名前のデータファイルなど）。

  ```bash
  node "$HOME/.claude/plugins/.../scripts/belta-init.js" set env_guard_exceptions "environment.env"
  ```
:::

止まったときは「鍵の中身を見ずに済む方法」に切り替えてください。たとえば、設定の**名前だけ**を扱う、サンプルファイル（`.env.example`）を見る、値そのものはあなたが入力する――といった進め方です。

## L2: permission allowlist

**結論**：これは「**操作ごとの通行許可証**」です。操作ルール（permission）が、操作の種類ごとに 3 段階で対応を決めます。見るだけは自由（allow）、送る・作るは一声確認（ask）、危険な操作は通行禁止（deny）です。

ルールが重なったときは、**厳しい方を優先**します（deny ＞ ask ＞ allow）。どのルールにも当てはまらない操作は、念のため既定で「確認する（ask）」になります。

| 分類 | 意味 | 利用者から見た挙動 | 例 |
| --- | --- | --- | --- |
| **allow**（やってよい） | 読み取り・安全な操作 | 確認なしで実行 | `Read`、`gh pr list`、Notion/Slack/Drive の検索・閲覧 |
| **ask**（確認する） | 書き込み・外部に影響あり | **毎回確認が出る** | Slack 送信、Notion/PR 作成、`git push` / `commit`、`curl` / `wget` |
| **deny**（禁止） | 取り返しのつかない操作 | **実行できない** | `rm -rf`、`sudo`、`git push --force`、`gh repo delete`、各種 `*delete*` |

具体例で言うと、こうなります。

- `gh pr list`（一覧を見るだけ）→ 確認なしで通る。
- `slack_send_message`（Slack に送信）→ 確認が出る。
- `gh issue create`（issue を作成）→ 確認が出る。
- `rm -rf ...` / `git push --force`（取り返しのつかない操作）→ ブロックされる。
- `.env` の中身の読み取り（`Read(.env)` / `cat .env`、認証情報が入りがちなファイル）→ ブロックされる。

::: info L1 と L2 は独立しています
通行許可証（permission）で「送ってよい」と承認しても、中身に個人情報が混じっていれば、最後の検査官（L1）が止めます。逆に、L1 を通っても通行禁止の操作は L2 が止めます。二重のゲートでお互いを補い合います。
:::

権限ルールは同梱の `.claude/settings.json` で配布されます。環境によって自動マージが効かない場合は、導入手順の **[Step 6](/guide/getting-started#step-6-権限ルールの適用-必要な場合のみ)** で手動適用できます。

## 仮想の個室で作業する（サンドボックス）

**結論**：コマンドの実行は「**仮想の個室**」の中で行われます。持ち出せる物（読み書きできるファイル）と連絡先（通信できる相手）をあらかじめ決めておくので、**うっかりした操作や、外から紛れ込んだ怪しい指示があっても、被害が部屋の外に広がりません**。

普段の使い方は変わりません。個室では次の境界が守られます。

| 境界 | 既定 |
| --- | --- |
| 書き込める場所 | 作業中のフォルダと一時フォルダだけ |
| 読める場所 | ほぼ全体。ただし **鍵の保管場所（`~/.ssh` / `~/.aws` / `gh` の設定）は読めません** |
| 通信できる相手 | GitHub と npm（部品の取得元）だけ。他は必要になったときに確認 |

::: tip 個室で動かない作業も止まりません
一部の道具は個室の中では正常に動きません（ブラウザを開く認証、`docker` など）。その場合、これまでと同じ**確認ダイアログを経て個室の外で実行**できます。**仕事が止まらない運用**にしてあります。
:::

::: warning Windows をお使いの方へ
仮想の個室は macOS・Linux・WSL2 で動きます。**Windows でそのまま使っている場合、個室は使われません**（設定が入っていても不具合は起きません）。この場合も L1（検査官）と L2（通行許可証）はこれまで通り働くので、守りが無くなるわけではありません。より強く守りたい場合は WSL2 の中で Claude Code を使ってください。
:::

いまの状態は `/sandbox` で確認できます（動作モード・除外設定・実際に効いている設定が見えます）。設定を専用フォルダへ反映するコマンドは次のとおりです（初回セットアップで実行済みです）。

```bash
node "$HOME/.claude/plugins/.../scripts/apply-governance.js" --target "$HOME/my-agent/.claude/settings.local.json"
```

## 使えるアプリ連携とスキルを絞る

**結論**：**出入りを許した業者だけ通す**考え方で、使えるアプリ連携（Notion・Slack・Google Drive など）と、動かせる道具（スキル）を絞っています。知らないうちに別のアプリへ情報が渡ったり、覚えのない道具が勝手に動いたりしません。

### アプリ連携（MCP）の許可リスト

許可しているのは、オンボーディングでつないだアプリ連携だけです。それ以外は使えません。

::: warning つなぎ直したときは名前の確認を
アプリ連携の「名前」は環境によって変わります（英語名のこともあれば、長い記号列のこともあります）。**名前がずれると、そのアプリが使えなくなります**。新しくアプリをつないだら `/mcp` で実際の名前を確認し、上のガバナンス反映コマンドに `--mcp-servers "<実際の名前1>,<実際の名前2>"` を付けて実行してください。
:::

### スキル（道具）の許可リスト

次のいずれかに当てはまるスキルは、これまで通りそのまま動きます。

- このエージェントに最初から入っているスキル
- あなたが導入して記録されているスキル（`/skill-suggest` などで入れたもの）
- Anthropic 公式のスキル（PDF・スプレッドシート・スライドなど）

上のどれにも当てはまらないスキルが動こうとしたときだけ、**「導入した覚えがありますか？」という確認**が出ます。自分で入れたものなら許可して構いません。心当たりがなければ拒否してください。

### 新しいスキルの安全性チェック

**結論**：外から持ってきたスキルは、入れる前に**中身を機械的に検査**します。人が目で見落としがちな危ない書き方を、決まった手順で洗い出す検査です。

検査で見つけるもの：取り消しにくい操作（ファイルの一括削除など）／鍵を外部へ送る書き方／中身を隠して実行する書き方／エージェント自身の設定を書き換える動き／発火条件の書き忘れ。

```bash
node "$HOME/.claude/plugins/.../scripts/skill-audit.js" --dir <スキルのフォルダ>
```

::: warning 検査を通っても「安全のお墨付き」ではありません
この検査は、あらかじめ決めた危ない書き方を見つけるものです。実行時に外から新しいコードを取ってくるような手口は、原理的に見つけられません。**提供元がはっきりしないスキルは、検査を通っても入れない**のが安全です。
:::

## 作業に応じて賢さを使い分ける

**結論**：**用件の重さに合わせて、担当する頭脳（モデル）を切り替えます**。「考える必要がある仕事にはじっくり考える頭脳を、単純作業には軽い頭脳を」という割り振りです。あなたが指定する必要はありません。

- **設計・最終チェック・レビュー**：もっとも賢い頭脳が担当します。とくに「この内容は正しいか」を**判定する**作業は、必ず上位の頭脳に確認させます（軽い頭脳だけで結論を出させません）。
- **通常の実装・文章作成**：標準の頭脳。
- **整形・一括処理・集計**：軽い頭脳、または計算だけで済む部分は**プログラム**（頭脳を使わない＝速くて確実）。

もっとも高価な頭脳（例外枠）は既定では使いません。使おうとすると**確認ダイアログが出る**ようになっているので、気づかないうちに費用がかさむことはありません。消費が気になったら `/usage` で内訳を確認できます。

## 止まった記録は残ります（監査ログ）

**結論**：何かがブロックされたとき、「**いつ・どの操作で・何が理由で止まったか**」だけが手元のパソコンに記録されます。あとから調べるための最初の手がかりです。

- 保存先：あなたのパソコン内の個人フォルダ（`~/.belta/audit/security/`。POSIX: `$HOME` / Windows: `%USERPROFILE%` から解決）。90 日で古い分は自動的に消えます。
- **中身（機密そのもの）は記録しません。** 機密を止めるための記録が、機密の写しになってしまわないようにしています。
- 外部には送信されません。
- **守りの設定そのものが書き換わったときも記録されます。** 操作ルールを書いた設定ファイルが会話中に変更されると、「どの設定ファイルが変わったか」だけが同じ場所に残ります（変更の中身は残しません）。止めることはしません＝業務で必要な変更を妨げないためで、記録だけを残します。

## 会社として外せないルールにする（managed settings）

**結論**：ここまでの守り（L1・L2・個室）は、**あなたのパソコンの設定ファイルに置かれている**ため、その気になれば自分で外せます。会社として「誰も外せないルール」にしたい場合は、**会社が配る、外せないルールブック（managed settings）** を使います。これは情シス推進担当の作業で、利用者側の操作は不要です。

::: info 一般の利用者の方はここを読み飛ばして構いません
この章は導入を管理する担当者向けです。あなたの手元の設定は、初回セットアップで既に適用済みです。
:::

### なぜ必要か

いまの配り方は「各自の設定ファイルに書き込む」方式です。**もっとも困るのは、見張り役（フック）を丸ごと止める設定を利用者が入れられること**で、そうなると個人情報の検知（L1）と道具の許可チェックが同時に効かなくなります。外せないルールブックだけが、この経路を塞げます。

### 配り方は 2 通り

BELTA は Claude for Teams プランなので、**専用の端末管理ソフト（MDM）を入れていなくても今日から使えます**。

| 方式 | 必要なもの | 手順 |
| --- | --- | --- |
| **claude.ai から配る**（推奨） | Teams / Enterprise プラン、組織の Owner 権限 | claude.ai の管理画面（Admin Settings > Claude Code > Managed settings）に設定を貼って保存するだけ。全員の Claude Code が起動時と 1 時間ごとに自動で受け取ります |
| **端末に置いて配る** | 端末管理ソフト（MDM）または手作業 | 各パソコンの決まった場所に設定ファイルを置きます。OS がファイルを守れるので、こちらの方が強く縛れます |

貼り付ける設定の完成版と、置換が必要な箇所（組織の識別子・アプリ連携の名前）は、プラグイン同梱の `plugins/workflow/examples/managed-settings.json` と、同じフォルダの `README.md` にあります。

### 何を縛るか（要点だけ）

- **操作ルールを会社の設定だけに固定する** — 利用者が「やってよい」を勝手に増やせなくなります。
- **見張り役（フック）を止められないようにする** — 上で書いた、いちばん困る穴を塞ぎます。
- **使えるアプリ連携を会社の許可リストだけに固定する。**
- **未審査の道具の持ち込み経路を塞ぐ** — 出所不明のプラグインやスキルを、起動時のオプションで横から入れることもできなくなります。
- **個人アカウントでの利用を禁止し、会社のアカウントに固定する。**
- **古いバージョンの Claude Code では起動させない** — 既知の弱点が残ったまま使われるのを防ぎます。

::: warning 過信しないでください
外せないルールブックといっても、**端末管理ソフトを入れていない場合は「強い推奨」程度の強さ**です（設定を消しても次回受信で戻る、程度）。本当に厳格に縛るには端末管理ソフトでの配布が必要です。詳しい限界は同梱の `README.md` に書いてあります。
:::

## L3: Git 漏洩防止

**結論**：これは「**保存（コミット）するときに荷物の中身をスキャンする検査ゲート**」です。あなたがリポジトリに保存・送信する操作（commit / push）をした瞬間、機密の混入を見つける検査（gitleaks）が中身を自動でスキャンします。

具体的には、`.gitleaks.toml` と GitHub Actions（`secret-scan.yml`）が、マイナンバー / クレジットカード / メールアドレスの一括掲載 / パスワードの直書き / 機密ラベル / 社内ドメイン / よくある API キーの形を見つけます。混入が見つかると、保存処理（CI）が止まり、先へ進めなくなります。最後の砦として、機密がリポジトリに残るのを防ぎます。

## 認証情報の扱い（やってよいこと / いけないこと）

**結論**：パスワードや API キー（システムにログインするための鍵）は、**文章やファイルに直接書かない**でください。鍵は OS の金庫や claude.ai 側の安全な保管庫が預かります。

### ❌ やってはいけない

- API キー・トークン・パスワードを `profile.md` / `notes/` / リポジトリに書く。
- 認証情報をスクリプトや設定ファイルに直書きする。
- Slack / Notion などに認証情報を貼り付けて共有する。

### ✅ 守ること

- 認証は「許可」ボタンで安全につなぐ方式（OAuth）を使います。Notion / Slack / Google Drive の鍵は claude.ai 側の保管庫に、GitHub の鍵は OS が暗号化して鍵を保管する金庫（macOS の keychain / Windows の資格情報マネージャー）に預けられます。手元に平文（そのまま読める形）では残りません。
- 個人データ（`~/.belta/` 配下）はリポジトリに保存しない。`.gitignore` で除外済みです。

## 万一、機密情報を出してしまったら

落ち着いて、上から順に対応してください。とくに **4 番（鍵の無効化と再発行）** は忘れがちですが必須です。削除しただけでは、すでに見られた鍵は使われ続ける恐れがあります。

::: danger 漏らしたと気づいたら、この順で対応
1. **止める（STOP）** — 進行中の送信や保存（commit）を直ちに止める。
2. **範囲を特定** — どの情報が、どのツール・チャンネル・リポジトリに出たかを確認する。
3. **消す** — 送信済みなら削除する（Slack メッセージの削除 / Notion ページの修正 / 保存の取り消し）。保存履歴（Git 履歴）に入った秘密は、履歴からも消す。
4. **鍵の無効化と再発行（ローテーション）** — 露出した認証情報は**必ず無効化して作り直す**。削除だけでは不十分。
5. **横展開の確認** — 同じような漏れが他にないか確認する。
6. **記録して報告** — 経緯と対処を `~/.belta/notes/` に残し（機密の中身そのものは書かない）、情シス推進担当へ報告する。
:::
